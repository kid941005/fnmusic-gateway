## 二、严重（P0）

| 编号 | 问题 | 影响 | 修复内容 |
|---|---|---|---|
| P0-1 | `call_tool` 一进入就调用 `provider()` | NAS/飞牛掉线时，`music_sources`、`music_storage`、`music_status` 全部失败，恰好在排障时不可用 | 新增 `_LazyProvider`，按实际分支惰性构造 provider；三个管理/状态工具不再依赖飞牛可达性 |
| P0-2 | `FallbackProvider` 内部新建 `LibraryStore` 未传 `max_bytes` | `music_favorite(action=add)` 的在线歌曲下载走 `download_ext`，绕过 `GW_LIBRARY_MAX_BYTES`，可能写满磁盘 | `FallbackProvider.__init__(..., max_bytes=0)`，由 `app.py` 传入 `LIBRARY_MAX_BYTES` |
| P0-3 | `fnmusic_client` 默认关闭 TLS 证书校验 | 若配置为 HTTPS，中间人可截获飞牛账号与 token | 默认 `ssl.create_default_context()` 正常校验；仅显式 `FNMUSIC_INSECURE_TLS=1` 才关闭（内网自签场景） |
| P0-4 | 飞牛前端协议常量 `API_SECRET` / `API_KEY` / `DEFAULT_DEVICE_ID` 硬编码 | 换部署环境或上游变更时需改源码，且容易误当用户密码泄露 | 支持 `FNMUSIC_API_SECRET` / `FNMUSIC_API_KEY` / `FNMUSIC_DEFAULT_BASE` / `FNMUSIC_DEFAULT_USERNAME` / `FNMUSIC_DEFAULT_DEVICE_ID` 覆盖；文档注明是协议常量而非用户密码 |

## 三、高（P1）

| 编号 | 问题 | 影响 | 修复内容 |
|---|---|---|---|
| P1-1 | `music_sources` 读取 `service` / `ok`，而 `source_status` 返回 `source` / `healthy` | 输出永远是「None（url） 不可用」，无法判断音源健康 | 统一改为 `item.get("source")` / `item.get("healthy")`，并补测试 |
| P1-2 | `lyrics_for` 只让 `fetch_lyrics` 受 `GW_LYRICS` 控制，在线音源分支仍会请求歌词 | `GW_LYRICS=0` 时仍访问在线音源，违背关闭语义并增加延迟 | 函数入口统一 `if not LYRICS_ENABLED: return ""`；在线分支复用同一个 provider 实例 |
| P1-3 | `_env_bool` 只判断 `is None`，空字符串被当作 false | `GW_TEE_SAVE=""` 会关闭边播边存，而不是使用默认 true；其他布尔配置同样受影响 | 空串/纯空白视为未设置，返回默认值 |
| P1-4 | `MediaCache.evict` 在 `max=0` 时执行总量比较并删除缓存 | `max=0` 表示不限容量，却会把缓存删光 | `if self.max <= 0: return`；与 `GW_LIBRARY_MAX_BYTES=0` 的语义保持一致 |
| P1-5 | `PlaybackService` 生成 `lyric_url` 未捕获异常 | 歌词查询/签名异常会让整个 `/api/play` / `music_play` 失败 | 包裹 `try/except`，失败时降级空歌词并继续播放 |
| P1-6 | `save_from_provider` / `MediaCache._stream` / `FallbackProvider.stream` 用 `except TypeError` 探测 `stream` 签名 | provider 内部真实抛出的 `TypeError` 会被误当成「不支持 quality」并重复请求，掩盖真实错误 | 新增 `_call_stream`，用 `inspect.signature` 判断是否接受 `quality`，统一调用 |
| P1-7 | `ExtProvider.health` 用 `data.get("ok", True) is not False` | `ok=0` 时 `0 is not False` 为 True，误报健康 | 改为 `bool(data.get("ok", True))` 真值判断 |

## 四、中（P2）

| 编号 | 问题 | 影响 | 修复内容 |
|---|---|---|---|
| P2-1 | `save_bytes` 写 `.part` 后 `os.replace` 失败不清理 | 下载失败残留 `.part` 文件，长期占空间且难排查 | `try/except` 中删除 `.part` 后再抛出 |
| P2-2 | `parse_spec` 用 `partition("@")` 直接切 `type@url` | URL 本身含 `@`（如带用户信息）时类型被误判 | 先识别 `^https?://`，整段作为 URL 并按端口推断类型 |
| P2-3 | `LibraryStore.stats` 统计目录内所有文件 | 封面、日志、临时文件被计入曲库容量，容量上限判断不准 | 只统计 `.mp3/.flac/.wav/.m4a/.ogg/.ape` |
| P2-4 | `LibraryStore._jobs` 只增不删 | 长期运行轻微内存泄漏 | `_run_job` 在 `finally` 中 `self._jobs.pop(guid)` |
| P2-5 | 未使用 import、死 `except BadRequest`、无文档 `q_quality` 别名 | 增加阅读成本，异常分支永远不可达 | 清理 `NotFound/UpstreamError/get_profile/ExtProvider/ext_split/threading/time` 等未用 import；删除 `except BadRequest` 死代码；`_handle_api_play` 去掉 `q_quality` |
| P2-6 | 文档与部署不一致：README/compose 仍写 9 个工具、引用不存在的 `.env.example`、`GW_PUBLIC_BASE` 默认指向 8766 管理口 | 新用户按文档部署会配置错误或无法复制 `.env` | 工具数 9→12；新增根目录 `.env.example`；4 份 compose 的 `GW_PUBLIC_BASE` 默认改 8767（公网播放口），README 同步 |

## 六、优化建议（本次未改，避免超出审计范围）

1. `ExtProvider.stream` 当前 `resp.read()` 一次性把整首音频读入内存；超大 FLAC 有 OOM 风险。建议改为流式写入临时文件或分块转码。
2. `MediaCache._locks` 按 guid 增长且不回收；可改为 `WeakValueDictionary` 或在缓存淘汰时同步清理。
3. `VERSION` 在 `app.py` 与 `gwlib/sources.py` 手工同步；建议收敛到单一 `gwlib/__init__.py` 常量。
4. `FallbackProvider.search` 目前每个音源最多返回 `search_limit` 条再合并；若在线源很多，可考虑增加总结果上限与超时预算。
5. 建议将本次修复整理为 2.0.1 发布（代码已通过 60 测试，但尚未 bump 版本/构建镜像）；是否发版需按部署节奏决定。
